# MindSpeak 界面视觉与交互体验审查

> **审查范围**：19 个页面 × 1440/390 两档视口 × 浅/深两套主题（`audit-shots/` 76 屏）
> **审查方法**：源码走查（`index.html` / `css/*.css` / `js/*.js`）+ 截图目视评审 + 关键像素取样与色相/对比度计算
> **与前一版的关系**：`docs/ui-audit-20261001.md` 是**程序化可访问性审计**（对比度、触控尺寸、溢出），P0/P1 已修复。
> 本文审查的是它未覆盖的层面：**设计语言的系统性、布局与信息层级、导航逻辑、反馈与状态**。
> 所有结论都附实测数据或 `文件:行号`，可直接定位复核。

---

## 一、结论摘要

界面的**单屏观感**是合格的：令牌体系完整、深浅双主题一致、无溢出、对比度达标。
问题集中在**跨屏的系统一致性**和**状态设计**上——即"每一屏单独看都还行，连起来用就散"。

按对用户的影响排序，四个最痛的根因：

| # | 根因 | 影响面 | 一句话 |
|---|---|---|---|
| 1 | 移动端底部导航的标签与实际页面**不是同一个语义** | 移动端**每一次**导航 | 点「练习」进的是语法练习，点「学习」进的是背单词 |
| 2 | 页面切换**不复位滚动位置** | 桌面端**每一次**切页 | 从滚到一半的设置页切到首页，仍然停在半空 |
| 3 | 空数据状态被渲染成"满负荷仪表盘" | **新用户第一印象** | 全是 0，却有 4 个彩色大数字、绿色「▲+0」、五轴全满的雷达图 |
| 4 | 设计令牌被大面积旁路 | 全部视觉 | 字号令牌采纳率 **18%**、192 个硬编码色值、暖冷边界色相相差 170° |

下面按 P0 → P3 展开。每条的格式是：**问题 → 证据 → 建议 → 预期效果**。

## P0 · 阻断核心任务或直接造成误解

### P0-1 底部导航：标签与实际目标不是同一个东西【导航逻辑】

**问题**
移动端 4 个底部 Tab 直接绑死在 4 个具体页面上，其中 3 个的标签语义与目标页不符：

| Tab 标签 | 实际 `data-tab` | 打开的页面 | 用户预期 |
|---|---|---|---|
| 首页 | `home` | 首页 | ✅ 一致 |
| **学习** | **`word`** | **背单词** | 以为进"学习"分区，结果直达单一页面 |
| **练习** | **`grammar`** | **语法练习** | 以为进"练习"分区，结果直达语法练习 |
| 我的 | `settings` | 设置 | ⚠️ 尚可，但见 P1-7 |

**证据**：`index.html:1729-1732`；`js/app.js:5755` 用 `b.dataset.tab === tab` 直接做高亮映射。

**影响**：这是移动端唯一的常驻导航。用户点「练习」看到语法填空，会合理推断"这个 App 的练习就是语法"，从此找不到拼写测试、听力训练、阅读训练、单词 PK——这 4 个真正的练习入口，只能靠汉堡菜单里的 19 项列表去翻。

**建议**
- 方案 A（推荐，改动小）：Tab 改为**容器语义 + 二级入口页**。新增极轻量的「练习」聚合页（卡片网格：拼写 / 听力 / 阅读 / 语法 / PK / 错题强化），Tab 指向它；「学习」同理指向 背单词 / 词文串学 / 收藏夹 的聚合页。复用现有 `.dash-quick-btn` 网格样式，零新增视觉语言。
- 方案 B：保留直达，但把标签改成真实名称（「背单词」「语法」）。缺点是底部 4 格浪费了 15 个页面的导航容量。
- 无论哪个方案，**侧边栏分组与底部 Tab 必须同源**，现在这两套体系互不映射。

**预期效果**：移动端可发现页面从 4 个提升到 19 个；消除"练习=语法"的错误心智模型；底部导航点击后的落差感消失。

### P0-2 页面切换不复位滚动位置【导航逻辑 / 布局结构】

**问题**
`<main class="content">`（`index.html:346`）是**唯一的滚动容器**，20 个 `.page` 都塞在里面，靠 `display:none/block` 切换。切换时没有任何滚动复位。

**证据**：`css/style.css:142` `.content{...overflow-y:auto}`；`js/app.js:5738-5794` 的 `showTab()` 全文没有 `scrollTop` / `scrollTo`。

**影响**：在设置页滚到底部改完选项，点侧边栏「首页」→ 首页停在半空，页标题和「开始学习」按钮都在视口外。用户的第一反应是"页面没加载完"或"卡住了"。

**建议**
```js
// showTab() 开头，在切换 .page 之前
var content = document.getElementById('main-content');
if (content) content.scrollTop = 0;
```
进阶：按 Tab 记忆各页滚动位置（`_scrollMemo[tab]`），返回时还原——对「设置」这类长页体验更好。

**预期效果**：每次导航都从页首开始，标题与主操作为首个可见元素；消除"页面坏了"的误判。

### P0-3 首页主操作不唯一：两个主按钮干同一件事【视觉层级 / 布局结构】

**问题**
首页首屏同时存在 **4 个启动入口、2 个视觉上的"主按钮"**：

| 入口 | 位置 | 样式 | 实际行为 |
|---|---|---|---|
| 开始学习 | 页面右上 | `.btn-primary` | `showTab('word')` |
| 去背单词 | 今日任务卡内 | `.btn-primary btn-sm` | `showTab('word')` |
| 立即测一测 | 底部卡片 | `.btn-primary` | 打开能力测评 |
| 快捷入口·背单词 | 快捷入口网格 | `.btn` | `showTab('word')` |

**证据**：`js/dashboard.js:217`（`btn-dash-start` → `showTab('word')`）；`index.html:397`（`data-goto="word"`）；`index.html:354`、`index.html:1414+`。

**影响**：首屏出现 3 个蓝色主按钮，用户要先做一次无意义的取舍；而"开始学习"这个最像主 CTA 的按钮，实际只是跳到背单词——名称与结果不符，点击后会觉得"就这？"。

**建议**
- 全页只保留**一个** primary：「开始学习」（右上），并让它做真实的事——按今日计划串起 背单词 → 复习 → 一个小任务，而不是等价于"去背单词"。
- 任务卡内的「去背单词」降为 `btn-secondary`（与「开始复习」「词文串学」同级），它本来就只是三个并列动作之一。
- 快捷入口整块降级为默认 `.btn`，不与主 CTA 抢注意力。

**预期效果**：首屏视觉焦点唯一；"开始学习"从标签变成一个真正有承诺的动作；用户不再需要在三个蓝色按钮之间猜。

### P0-4 AI hero 的主按钮是容器渐变的**反相**，按钮边界实测 1.03:1【配色搭配 / 视觉层级】

**问题**
`.ai-hero` 与它内部的主按钮用了**完全相反的同一条渐变**：

```css
/* css/nav.css:81  —— 深 → 浅 */
#page-ai .ai-hero { background: linear-gradient(135deg, var(--sage-deep), var(--sage-hover)); }
/* css/style.css:198 —— 浅 → 深 */
.btn-primary      { background: linear-gradient(135deg, var(--sage-hover), var(--sage-deep)); }
```

按钮放在 hero 里，两个渐变在同一位置正好互相抵消 → 按钮的填充与背景**几乎完全同色**。

**证据（像素取样，`audit-shots/mobile/ai-light.png`）**

| 取样点 | RGB | 对比 |
|---|---|---|
| 按钮填充 (250,230) | `(47,71,96)` | — |
| hero 同高度左侧 (100,230) | `(45,69,93)` | **1.03 : 1** |
| hero 左上角 (30,75) | `(43,65,88)` | 1.10 : 1 |

按钮只剩一条 1px 描边能看见，读起来像一个悬空的幽灵标签，而不是可点的 CTA。

**影响**：AI 页最想让人点的按钮，是全页最不可点的东西。这**不是个例**——`.btn-primary` 是全局组件，任何放在深色渐变底上的实例（`#page-ai .ai-hero`、番茄钟渐变区、AI 抽屉头部）都会重现。

**建议**
- 短修：在 hero 内给按钮换"反差材质"而非"同族渐变"——实心 `#FFFFFF` 底 + `var(--sage-deep)` 文字（实测 ≈8.9:1），是深色 hero 上最稳的主按钮写法。
- 根治：把渐变方向抽成令牌（`--brand-gradient-dir`），或规定"**按钮不使用与容器同族的渐变**"，在 design-system 里写成一条规则。

**预期效果**：主 CTA 的按钮边界从 1.03:1 提升到清晰的实心对比；深色渐变区上的按钮全部可辨。

### P0-5 零数据空状态 = 一屏"满负荷仪表盘"【视觉层级 / 布局结构】

**问题**
新用户（全部数据为 0）看到的首页和 AI 页，视觉密度与"活跃用户"完全相同：

- 首页 4 张统计卡：`0` 用 24px 粗体（`--text`，`css/dashboard.css:88`），与有值数据完全同一套强调；
  卡面另配四块**不同色系的彩色图标底**（珊瑚 / 蓝 / 蓝 / 琥珀，`css/dashboard.css:80-85`）
- 设置页 4 张卡：`0` 用 2.2rem 渐变强调字（`css/style.css:308`），每张还带一条**不同颜色的顶部彩条**
  （蓝 / 珊瑚 / 绿 / 红，`css/style.css:299-302`），值全是 0
- AI 周报：「`▲ +0` 较上周」——用**绿色 + 上三角**表达"持平"
- AI 能力雷达：五轴标注 词汇 `0` / 口语 `10` / 复习 `10` / 听力 `10` / 拼写 `10`，并绘制出一个**几乎填满的绿色多边形**

**证据**：`audit-shots/desktop/ai-light.png`、`audit-shots/desktop/settings-light.png`、`audit-shots/desktop/home-light.png`

**影响（三重）**
1. **视觉谎言**：0 数据的雷达图看起来很饱满，用户会以为自己"口语/听力/拼写都是满的"。雷达图的轴标签在无数据时展示的是**量程上限**而不是**用户值**，且没有刻度、图例、量程说明。
2. **注意力错配**：满屏彩色数字争夺注意力，但没有任何一个指向"我该做什么"。
3. **空状态缺失**：这是产品最关键的一屏（决定留存），却完全没有空状态设计——没有引导、没有示例、没有进度感。

**建议**
- **数字语义化**：`0` 用 `--text-tertiary` 弱化；只有非零值才用强调色。色彩只在"有值"时承担语义。
- **雷达图无数据时只画网格骨架**，多边形留空，并在中心写「完成一次测评后生成」；有数据时在轴端标注真实值而非量程。
- **「+0」不显示绿色上三角**——0 变化应当中性（灰），绿色只能表示"变好了"。
- **统计卡顶部彩条**在 0 值时统一为中性灰，有值时才上色（当前 4 条彩条的颜色并不对应语义，纯装饰）。
- **空状态卡片**：把「今日学习任务 0/10」替换成「还没有开始 · 花 3 分钟背 10 个词」+ 主按钮，让空状态自己完成转化。

**预期效果**：新用户首屏从"看不懂的一堆零"变成"知道下一步做什么"；雷达图不再传递错误的能力信息。

### P0-6 主题商店的兑换按钮在积分不足时仍是可点主按钮【操作反馈 / 表单交互】

**问题**
积分 0 的用户打开主题商店，8 张卡全部显示**同一种蓝色、同样可点的**「350 积分兑换」——没有置灰、没有差额提示、没有"还差多少"。

**证据**：`js/items.js:283` 无条件渲染 `<button class="btn btn-sm btn-primary" data-act="buy">`；积分校验在 `js/items.js:240-243` 点击后才执行，只弹一个 toast。

**影响**
违反"预防优于报错"（Nielsen #5）。用户要点 8 次、被拒 8 次，才知道自己远不够。而且**价格出现了两次**（`◇ 350 积分 · 永久拥有` + `350 积分兑换`），本来就冗余的信息，其中一条还不承担状态。

**建议**
- 积分 `< price` 时：按钮改 `btn-secondary` + `disabled`，文案改「还差 350 积分」；卡面价格行保留一处即可。
- 积分充足但未拥有：保持 primary「兑换」。
- 已拥有：弱化为「使用」（现有逻辑正确，可参考）。
- 「还差多少」比「需要多少」更有行动指向——前者暗示可以攒，后者只是拒绝。

**预期效果**：8 次无效点击变成 0 次；商店从"点了被拒"变成"展示目标"，积分体系有了正向牵引。

### P0-7 确认弹窗：Android 返回键关不掉，且没有对话框语义【表单交互 / 点击响应】

**问题 A · 返回键失效（可见 bug）**
Android 返回键处理里找的是 `.modal-overlay.active`：

```js
// js/app.js:5713
var modal = document.querySelector('.modal-overlay.active');
if (modal) { modal.classList.remove('active'); return; }
```

但项目里**从未存在过 `.modal-overlay` 这个类**（全仓库唯一出现处就是这一行）。真实的确认框是 `ConfirmBox` 创建的 `#modal-confirm.modal.hidden`（`js/app.js:147`）。

**后果**：确认框开着时按返回键 → 找不到弹窗 → 走「再按一次退出」→ **App 被退出，弹窗还悬着**。凡是"清空错题本""重置所有数据"这类危险操作触发的确认框，都会遇到。

**问题 B · 对话框语义缺失**
`#modal-confirm` 没有 `role="dialog"` / `aria-modal` / `aria-labelledby`；焦点只被 `focus()` 到取消按钮，**没有焦点陷阱**（Tab 可跑到弹窗背后的页面）；**没有 ESC 关闭**（只有侧边抽屉处理了 ESC，`js/app.js:5689`）。
（全项目唯一带 `role="dialog" aria-modal` 的是 AI 设置抽屉，`index.html:548`。）

**建议**
- 把选择器改成实际存在的形态：`document.querySelector('#modal-confirm:not(.hidden), .modal:not(.hidden)')`。
- 给 `ConfirmBox.init()` 的容器补 `role="dialog" aria-modal="true" aria-labelledby="confirm-title"`。
- 复用抽屉已有的焦点圈定逻辑（`js/app.js:5690-5697` 那段 Tab 循环）抽成通用函数，抽屉和弹窗共用。
- 全局加 ESC：弹窗打开时 `Esc` = 取消。

**预期效果**：危险操作不再能"把 App 退掉却留下弹窗"；键盘用户能 Tab 循环、Esc 退出；读屏用户能听到"对话框"。

### P0-8 词库未就绪时会**每 0.8 秒弹一条 toast**，且 toast 无上限【加载状态 / 操作反馈】

**问题**
词库脚本（约 9.8MB）异步加载，未就绪时：

```js
// js/assessment.js:401-405
if (typeof WORD_LIBRARY === 'undefined' || ...) {
  Toast.info('词库加载中，请稍候…');
  setTimeout(function() { self.start(); }, 800);   // ← 递归重试
  return;
}
```

而 toast 容器**没有去重、没有数量上限、没有 max-height**：

```css
/* css/style.css:1894 */
.toast-container{ position:fixed;top:80px;right:20px;
  display:flex;flex-direction:column;gap:10px; pointer-events:none; }
```

**影响**：慢手机首开（8 秒）→ 弹出约 10 条**完全相同**的 toast。每条约 52px + 10px 间距 ≈ 620px，**直接溢出一屏**，把整个界面糊住。用户此刻能做的只有等——而界面看起来像崩了。

**建议**
- 重试**不弹 toast**。改为在「开始测评」按钮上做就地 loading 态（按钮文字变「词库加载中…」+ 禁用 + 内联 spinner），重试逻辑照旧。
- Toast 容器加保护：`max-height:calc(100vh - 120px); overflow:hidden;`，`Toast.show()` 内做同文案去重（同 message 已存在则重置计时器而非新增）。
- 移动端把容器移到 `bottom:calc(88px + env(safe-area-inset-bottom))`，避开顶栏与页面标题。

**预期效果**：toast 从"刷屏糊屏"变成一条就地状态；任意数量的异步提示都不会挤爆视口。

## P1 · 明显影响体验，但不阻断任务

### P1-1 没有加载状态体系【加载状态】

**问题**：全项目搜索 `skeleton` / `spinner` / `aria-busy`，**CSS 中命中 0 次**（唯一的 `pull-refresh-spinner` 在 `css/android-animations.css:125`，且用于下拉刷新）。所有异步路径只有两种表达：**什么都没有**，或**一句 toast**。

**证据**：`grep -rn "skeleton|spinner|aria-busy" css/*.css js/app.js` → 无业务命中。AI 对话有打字指示器（`css/ai-chat.css:361`）是唯一例外，说明模式是有的，只是没推广。

**建议**：定义三个标准态并落到设计系统——
1. **内联按钮 loading**：`button.is-loading`（禁用 + 文字后缀省略号动画），覆盖所有"点击后要等"的按钮。
2. **区块骨架**：`.skeleton` 卡片（统计卡、图表、列表），首屏数据未就绪时替换内容而非留空。
3. **整页过场**：只在真正的长任务（能力测评生成试卷）使用。

**预期效果**：用户能区分"没数据"和"还在加载"；减少"点了没反应"的重复点击。

#### ✅ 已修复（第二批收尾，TDD 实现）

**先做了耗时实测再决定要不要加骨架**——`scripts/probe-loading-costs.mjs`（真实 Chromium，重复取中位数）：

| 候选路径 | 实测 | 结论 |
|---|---|---|
| 词库就绪窗口 | **603ms**（119987 词；慢机/慢网首达数秒） | 唯一值得上加载态的真实等待 |
| `createPaper` 生成试卷 | **17.4ms** | **否决整页过场** |

→ **对原建议第 3 条的更正**：给 17ms 的任务盖全屏遮罩只会制造一次闪烁，是负优化。方案改为**以词库窗口为核心**，不引入整页过场；这条结论已写进 `js/core/loading.js` 的注释与源码级守卫，防止以后凭直觉再加。

**落地形态**：`js/core/loading.js`（`window.Loading`，排在 `app.js` 之前加载，三张加载表同步注册）

| 能力 | 说明 |
|---|---|

### P1-2 背单词的翻转与切词**零动效**，是硬切【操作反馈 / 点击响应】

**问题**
- `flipCard()` 就是 `classList.toggle('hidden')` 两个 div（`js/app.js:2670-2680`）——**没有 3D 翻转、没有淡入、没有过渡**。
- `nextWord()` / `prevWord()` 只改索引后重渲染（`js/app.js:2678-2679`）——**没有切卡动画**。

**影响**：这是全 App 点击频率最高的两个交互。一个叫「翻转」的按钮做的是瞬间显隐，用户会怀疑自己"是不是点空了"。缺少运动反馈也让"评价已记录"这件事完全没有感知——`markWord()` 记完分就直接换下一张卡（`js/app.js:2879`），没有任何确认。

**建议**
- 翻转：`transform: rotateY(180deg)` + `backface-visibility:hidden` 的经典双面卡，180–220ms `ease-out`。
- 切卡：评价后卡片向对应方向划出（认识→右、不认识→左）+ 下一张从反方向淡入。方向上与"左右打分"的语义打通。
- 评价按钮：点击后 120ms 的按下态 + 短暂保留所选颜色（"记录中"），再切卡。
- 尊重 `prefers-reduced-motion`：降级为 120ms 交叉淡化（项目已有该媒体查询的写法，`css/mobile.css:502`）。

**预期效果**：最高频操作从"点了不知道有没有反应"变成有明确节奏的连续动作；评价结果不再需要靠"卡片变了"来反推。

### P1-3 全项目**没有手势**，卡片上一片死区【点击 / 手势响应】

**问题**：`js/app.js` 中 `touchstart` 仅出现 2 次，且都与语音解锁有关（`js/app.js:7232/7236`）；`touchmove` / `pointerdown` 无业务用途。**没有任何滑动交互。**

**影响**：移动端背单词时，切词只能点两个 36px 的小箭头（`#btn-prev` / `#btn-next`），或点底部评价按钮。390px 屏上，拇指自然滑动的位置（卡片本身）完全没有响应。同类产品（Anki、百词斩）的滑动切卡/上滑看答案已是肌肉记忆。

**建议**（按性价比排序）
1. **卡片左右滑** = 上一个 / 下一个（阈值 60px，带跟手位移 + 松手回弹）。
2. **卡片上滑** = 翻转。
3. **抽屉边缘右滑** = 打开汉堡菜单（现在是纯按钮）。
4. 用 `passive:true` 监听，纵向滚动不抢。

**预期效果**：单手可完成"看词→翻面→评价→下一张"全流程；移动端有效的可点面积从两个小箭头扩大到整张卡片。

### P1-4 键盘焦点环只覆盖了首页【点击响应 / 可访问性】

**问题**：全局**没有** `:focus-visible` 规则。仅有的几处是显式白名单：

css/dashboard.css:220   #page-home .dash-quick-btn:focus-visible
css/mobile.css:376-377  .sidebar.open .nav-btn / .btn-menu / .nav-group-title

**预期效果**：18 个页面恢复键盘可见焦点；已有的快捷键投入从"隐藏功能"变成"可学的能力"。

### P1-5 设置的保存模型不一致，且嵌套 label 会误触【表单交互】

**问题 A · 一半即时一半要保存**

| 控件 | 生效方式 |
|---|---|
| 主动回忆 / 自适应复习 / 番茄音效 / 语音即时 | `change` 即存 + 弹 toast（`js/app.js:5977-5980`） |
| 每日新词数量 | 必须点「保存设置」（`js/app.js:6251-6256`） |
| 自动保存 / 间隔分钟 | 第三套行为 |

同一屏里三种持久化模型，用户无法预判"我改完了吗"。

**问题 B · label 包裹了不相关的控件**
```html
<!-- index.html:1476-1479 -->
<label class="auto-save-toggle">
  <input type="checkbox" id="auto-save" checked> 自动保存
  <span class="auto-save-interval">每 <input type="number" id="auto-save-interval"> 分钟自动备份</span>
</label>
```
点「分钟自动备份」这几个字会**切换"自动保存"开关**。这是真实的数据破坏风险——用户以为在读说明，实际改了一个设置。

**建议**
- 统一为**即时生效**（现代设置页的默认），删掉「保存设置」按钮；数量输入用 `change` + 抖动防抖 500ms。
- 把长说明文案移出 `<label>`，只保留控件与短标签在 label 内；`auto-save-interval` 拆成独立 `<label for>`。
- 每个设置项统一为「左标签 + 右控件」的两列布局；给每一项补一行 `--text-tertiary` 的说明文字位（现在说明和控件混排）。

**预期效果**：改完即生效，不再有"忘点保存"；消除误切换自动保存的可能。

### P1-7 没有路由、没有返回栈、没有深链【导航逻辑】

**问题**：页面切换完全在内存里（`showTab()` 切 `.active` 类），**不改 hash、不 pushState**。唯一的 `pushState` 是抽屉（`js/app.js:5648`）。Android 返回键的逻辑是：抽屉 → 弹窗 → 否则「再按一次退出」（`js/app.js:5704-5736`）。

**影响**（三处）
1. 在「背单词」按返回键 → 不是回首页，而是提示"再按一次退出"。20 个页面之间没有退路。
2. 刷新页面 / 分享链接 → 一律回到首页，无法指向具体页面。
3. 浏览器前进后退按钮与 App 导航完全无关。

**建议**
- Tab 切换改写 `location.hash`（`#/word` 这种轻量路由即可），并监听 `hashchange` 反向驱动 `showTab()`。收益立竿见影：深链、刷新保持、浏览器历史。
- 返回键优先级改为：抽屉 → 弹窗 → **非首页则回首页** → 双击退出。
- 首页作为"根"，其余页面都从首页可达——现在这一点成立（首页有快捷入口），所以回首页是天然合理的退路。

**预期效果**：返回键从"要么无效要么退出 App"变成符合直觉的逐层后退；页面可分享、可收藏。

#### ✅ 已修复（第三批，TDD 实现）

**落地形态**（`js/app.js`）：

| 能力 | 实现 |
|---|---|
| 切页写 hash | `showTab()` 用 `history.replaceState({msTab}, '', '#/'+tab)` |
| hash 反向驱动 | `_initHashRouting()` 监听 `hashchange` → `showTab()`；未知 hash 由 `_tabFromHash()` 挡掉（校验 `#/xxx` 必须对应真实存在的 `#page-xxx`，否则界面会被带到一个没有 `.active` 的空白区） |
| 深链 / 刷新保持 | 构造末尾读 `_tabFromHash()`，命中则 `showTab()`；未命中时补写 `#/home`，否则用户复制地址栏拿到的是不带页面信息的裸链接 |
| 返回键 | 优先级抽成 `App.prototype._onBackPressed()`：抽屉 → 确认框 → 其它可见弹窗 → **非首页则回首页** → 双击退出。原来这段埋在 Capacitor 回调里，没法写测试 |

**两条实测才发现的取舍与坑**：

1. **首屏 hash 为空**：深链只在命中 hash 时 `showTab()`，无 hash 时地址栏一直是裸链接。已补写 `#/home`（真实浏览器验收时抓到）。
2. **浏览器前进/后退曾在一段时期内刻意未打通，现已打通**（当时的说明保留在此，因为它是后续重构的直接原因）：切页用 `replaceState`，不压历史条目，所以浏览器后退会退到上一个文档而不是应用内切页。之所以这么取舍，是因为抽屉打开时会 `pushState({msDrawer})` 占位、`showTab()` 里还有一次 `history.back()` 去回收它；若切页也 `pushState`，那次回收会与 `hashchange` 反向驱动互相打断（实测会切了又弹回去）。

   **后续是怎么把它做完的**（见本节末尾「剩余 4 项」里的 P1-7 回归）：先把"抽屉占位靠 `history.back()` 异步回收"这个**冲突根源**换掉——改成在切页时把那条占位条目**同步改写**成本页条目（`replaceState`）。根源消失后，切页就可以放心地 `pushState`，浏览器前进/后退天然打通，无需另做历史栈管理。

   现在的行为：切 word → practice → settings，浏览器后退依次回到 practice、word，前进回到 practice；退到栈底时界面仍完整。真实浏览器验收 `scripts/verify-routing.mjs` 12/12。

**新增**：`tests/core/routing.test.js`（14 条行为级）、`scripts/verify-routing.mjs`（真实浏览器验收，12/12）。

**测试踩坑**：`history.back()` / `forward()` 在 jsdom 里**不可信**——初版写了两条用例，它们"立刻就通过了"，测的其实是 jsdom 的实现而不是我们的代码，已删除，改用真实浏览器验证。另外只改 hash 的 `Page.navigate` 是**同文档跳转**、不会重载应用，验深链时必须带 query 参数强制真实加载。

### P2-1 字体排布：字号令牌采纳率只有 **18%**【字体排布】

**实测数据**（对 `design-system.css` + `style.css` + `mobile.css` + `dashboard.css` + `ai-chat.css` + `nav.css` + `items.css` + `theme-fx.css` + `android.css` + `wordlist.css` + `listening-fav.css` 统计）

| `font-size` 硬编码声明 | **339** 处 |
| 硬编码字号去重后 | **49** 个不同值 |
| 设计系统定义的字号令牌 | **7** 个（12/14/16/18/20/24/30px） |

硬编码值里有一串**肉眼分不出、但确实不同**的阶梯：

- 同步补充**行高与字重的配对令牌**（现在行高散落在各处），否则字号统一了、呼吸感仍不齐。

**预期效果**：字号种类从 49+7 收敛到 8，层级一眼可辨；后续新增页面不会继续稀释。

### P2-2 间距留白：8pt 栅格被 4 个脱轨值稀释【间距留白】

**实测数据**：`padding` / `margin` 中 `var(--sp-*)` 引用 **404** 处（采纳率是好的），但硬编码 px 仍有：

| 值 | 出现次数 | 是否在 8pt 栅格 |
|---|---|---|
| 12px | 49 | ❌（栅格为 8/16/24/32） |
| 16px | 47 | ✅ |
| 8px | 45 | ✅ |
| **10px** | 38 | ❌ |
| **14px** | 29 | ❌ |
| **6px** | 28 | ❌ |
| 24px | 6 | ✅ |

脱轨值合计 **约 144 次**。10px / 14px / 6px 是最典型的"手工微调痕迹"——某个元素看着差点就手动挪 2px。

**预期效果**：页面的纵向节奏从"每处差一点"变成可预期的韵律；改一处间距不会牵动别处。

### P2-3 配色搭配：192 个硬编码色值 + 暖冷色温冲突【配色搭配】

**实测数据**

| 指标 | 数值 |
|---|---|
| 硬编码 hex 去重 | **192** 个（共出现 388 次） |
| `rgba()` 字面量 | **328** 处 |
| `#fff` / `#ffffff` 混用 | 55 次 / 5 次 |

**具体两类问题：**

**(a) 同一个"蓝"有 8 个版本**——`#4a6f93`(10) · `#5b82a6`(6) · `#5e8fb8`(7) · `#3a63b8`(7) · `#3e5f7f`(5) · `#9fc5e4`(3) · `#2563eb`(3) · `#e4ebf7`(4)。这些几乎都是 `--sage` 家族的"手抄变体"，本该全部走令牌。

**(b) 色温冲突（可量化的"脏"感）**

| 令牌 | 值 | 色相 | 观感 |
|---|---|---|---|
| `--ivory` | `#F4F6F8` | **H210°** | 冷灰白 |
| `--sage` | `#5B82A6` | **H209°** | 雾霾蓝 |
| `--sage-surface` | `#EEF4F9` | **H207°** | 冷蓝面 |
| **`--border`** | `#E5E2DC` | **H40°** | **暖米色** |
| **`--border-light`** | `#EDEAE5` | **H37°** | **暖米色** |

表面全在 H207–210°，而所有**卡片描边、进度条轨道、分隔线**都在 H37–40° —— **色相相差 170°，正好在对立面**。这是一套"暖米白 + 绿色 sage"时代的遗留：`css/design-system.css:6` 的注释至今写着 `60% Warm Ivory | 30% Deep Sage | 10% Warm Coral`，而 `--sage` 的实际取值早已是雾霾蓝。

**(c) 语义色是 Material 库存色，与自研品牌色不同血统**

| 令牌 | 值 | 色相 / 饱和 / 明度 |
|---|---|---|
| `--sage`（品牌） | `#5B82A6` | H209° / **S30%** / L50% |
| `--coral`（品牌） | `#FF8A65` | H14° / **S100%** / L70% |
| `--success` | `#4CAF50` | H122° / **S39%** / L49% |
| `--warning` | `#FFA726` | H36° / **S100%** / L57% |
| `--info` | `#42A5F5` | H207° / **S90%** / L61% |

首页 4 张统计卡的图标底色正好把这 4 个家族摆在一起（珊瑚 / 蓝 / 绿 / 琥珀），饱和度在 30% 与 100% 之间跳变——这就是"像拼凑的"来源。另外 `--info`(H207° S90%) 与 `--sage`(H209° S30%) **色相几乎相同**，却因饱和/明度差异巨大而被当成两种颜色，容易被误认为同一层级。

**建议**
- **修边界色温**：`--border` → `#E4E8EC`、`--border-light` → `#EDF1F4`（吸附到 H210° 家族）。
- **统一语义色血统**：success/warning 向品牌色的饱和度区间靠（建议 S 45–70%、L 48–58%），例如 `--success:#4E9E7A`、`--warning:#E0A040`。
- **清理 `--info`**：与 `--sage` 合并，或明确拉开（改向青 H190°），避免"两种蓝"。
- **补一层"色相家族"令牌**：`--hue-brand:209`、`--hue-accent:14`、`--hue-neutral:210`，让"能不能用这个色相"成为可检查的规则。
- 新增 16 套主题色包（`js/items.js`）也必须满足以上三条——现在主题包各自定义了一整套 12 个核心色，是硬编码颜色的另一个来源。

**预期效果**：界面从"每个组件都稍微偏一点"变成统一的冷调质感；新增颜色时有据可依。

### P2-4 令牌命名与实际值矛盾，`design-system.css` 被 `style.css` 静默覆盖【字体排布 / 配色搭配 · 交接风险】

**(a) 名字骗人**
`--sage` 实际是 `#5B82A6` —— **雾霾蓝，不是鼠尾草绿**。`--coral` 是 `#FF8A65`（偏橙）。文件头注释仍写 "Warm Ivory / Deep Sage / Warm Coral"。
任何按名字取色的新人（`color: var(--sage)` 期望绿）都会拿到蓝。这是纯认知成本，且会持续产生新的错误用色。

**(b) 组件库有一半规则是死代码**
`design-system.css` 与 `style.css` 都定义了 `.btn-primary`，且**外观不同**：

```css
/* css/design-system.css:362 —— 实色 */
.btn-primary { background: var(--sage); color: var(--text-inverse); box-shadow: var(--shadow-sage); }
/* css/style.css:194 —— 渐变（后加载，胜出） */
.btn-primary { background: linear-gradient(135deg,var(--sage-hover),var(--sage-deep)); ... }
```

加载顺序 `index.html:40→42` 决定 `style.css` 永远赢。**改 `design-system.css` 里的组件样式不会生效**——这会在设计交接时造成"我改了，但页面没变"的反复。

**建议**
- 令牌改名或加双向别名：保留 `--sage`（避免大范围重构）但补 `--brand-blue: var(--sage)` 并更新注释与文件头描述；新代码一律用语义名。
- 明确**单一事实来源**：`design-system.css` 只放令牌 + 基础组件（按钮/输入/卡片），`style.css` 只放页面级布局。把重复的组件规则从 `style.css` 里删掉（或反向合并）。
- 加一条轻量检查脚本：扫描两个文件里重复的选择器，输出冲突清单。

**预期效果**：改设计系统真的会生效；新人不需要读 87KB 的 legacy 文件才知道"哪个才是真的"。

### P2-5 圆角：两套命名 + 10 个脱轨值【间距留白 / 视觉层级】

- 令牌只有 6 档：`--radius-xs/sm/md/lg/xl/full` = 4/8/12/16/20/9999
- 但 CSS 里同时使用 **`--r-*`（92 次）与 `--radius-*`（60 次）两套等价别名**（`css/style.css:20-24` 做映射）——同一个值两种写法，容易写错也不会报错
- 脱轨值：`5px`(3) · `3px`(3) · `18px`(3) · `6px`(2) · `16px`(2) · `12px`(2) · `10px`(1)

最明显的是移动端底部导航：外壳 `border-radius:22px`、内部按钮 `18px`（`css/mobile.css:127/143`），而全局圆角档位里**没有 22px 和 18px**。

**建议**：删掉 `--r-*` 别名（或反向统一到 `--r-*`），把 22/18 吸附到 `--radius-xl(20)`，10px→`--radius-sm(8)` 或 `--radius-md(12)`，3/5/6px→`--radius-xs(4)`。

**预期效果**：圆角从 10+ 档收敛到 6 档，卡片/按钮/胶囊之间形成可辨认的三级层次。

### P2-6 图标体系混杂：SVG sprite + emoji + 字母字形【视觉层级】

同一个侧边栏和首页里并存三种"图标"：

| 类型 | 例子 |
|---|---|
| SVG sprite（`#i-*`，stroke 1.5–2px） | 侧边栏全部、首页快捷入口大部分 |
| **emoji** | 「支持开发者」的 🎉、兑换成功的 `Toast.success('🎨 兑换成功…')`（`js/items.js:248`） |
| **字母 / 文字字形** | 「背单词」用字母 `A`、「故事」用 `T`、「单词语境」用 `T` |

emoji 在不同系统渲染成完全不同的形状与色彩（Windows 彩色、部分环境单色），是全屏最"跳出"的元素；字母字形与 SVG 的线宽也对不齐。

**建议**：为 🎉 / 🎨 这类补 `#i-gift`、`#i-palette` 的 SVG 版本（sprite 里已有 `#i-gift`）；字母字形统一换成现有 SVG 或用同字重的文本徽章并固定尺寸。建立"**图标只用 SVG sprite**"的规则。

**预期效果**：全站图标线宽与视觉重量一致；跨平台观感稳定。

### P2-9 Toast 的可用性欠账【操作反馈】

| 问题 | 证据 |
|---|---|
| 无 `role="status"` / `aria-live`，读屏用户收不到任何操作反馈 | 全项目 `aria-live` 仅 2 处，都在非 toast 元素（`index.html:407/504`） |
| 无法手动关闭（`pointer-events:none`，无关闭按钮） | `css/style.css:1897` |
| 固定 3 秒，长文案读不完 | `js/app.js:116` |
| 切换主题也弹 toast（整屏都变了，不需要告知） | `js/app.js:1852` |
| 每个开关拨动都弹 toast，5 个开关 = 5 条噪音 | `js/app.js:5979` |
| 移动端定位沿用桌面坐标 `top:80px;right:20px`，压在页面标题区 | `css/style.css:1895` |

**建议**：容器补 `role="status" aria-live="polite"`；错误类（`toast-error`）加 `role="alert"`；给 toast 一个关闭按钮（容器改 `pointer-events:none`，单个 toast `pointer-events:auto`）；时长按字数自适应（`1600 + 字数×80ms`）；**开关类操作不弹 toast**（状态自明）；移动端容器改到底部安全区之上。

**预期效果**：反馈对读屏可达；toast 从"噪音源"回到"必要的确认"。

## 三、值得保留的优点（重构时不要动）

审查里也有做得扎实、不该在改版中被牺牲的部分：

1. **令牌体系骨架完整** — 颜色/字号/间距/圆角/阴影/层级六类令牌齐全，`style.css:20-24` 的 legacy 别名映射保证了没有断链变量。问题在"采纳率"，不在"有没有"。
2. **深浅双主题是真的一致** — 76 屏中未发现深色模式遗漏的组件（连 `--bubble-user-bg`、`.word-pos`、AI hero 都有专门的深色映射，并在注释里写明了对比度依据）。
3. **对比度与触控尺寸经过实测** — 上一轮审计用真实 Chromium 逐屏量化并全部修复，移动端触控目标已达标。新改动请保持这个标准（本文新增的按钮/滑块建议都按同一标尺给值）。
4. **工程防御意识到位** — `Toast` + `ConfirmBox` 替代了原生 `alert/confirm`（微信 webview 兼容）、事件总线解耦模块、防重入锁（`_evalLock` / `_generating`）、词库未就绪自动重试。这些是好底子，本文的建议都是在它们之上补状态层。
5. **移动端平台适配细致** — `env(safe-area-inset-*)`、`100dvh`（Android）、`backdrop-filter` 不支持时的实体底回退、iOS 输入框字号≥16px 防缩放。P0-1 的导航改动只需换 `data-tab`，不需要碰这套适配。

**顺带修掉一个真机才能复现的导航 bug（P1-7 的回归）**

开抽屉（`pushState({msDrawer})` 占位）后点导航项 → 页面切过去后 **300ms 内被弹回原页**。

成因：`showTab()` 先写 `#/settings`，随后回收抽屉占位的 `history.back()` 落地，把 hash 拉回 `#/home`；那一次 hash 变化被 `hashchange` 路由监听读成"用户切页"，于是把刚切好的页面弹了回去。单元测试全绿（jsdom 的会话历史不触发这套时序），是**真实浏览器验收**才抓到的。

修复：`showTab()` 检测到"正在回收抽屉占位"时**不立刻写 hash**，改由 `popstate` 处理器在回收完成后调用 `_writeHash()` 对齐（`_writeHash` 现在是 hash 的唯一写入口）。回归防线：`tests/core/routing.test.js` 的契约测试 + `scripts/verify-nav-metrics.mjs` 里的真机断言（开抽屉 → 点番茄钟 → 1.6s 后仍停在该页）。
