**审查对象**：<https://workbuddy.link/p/4tQYFm6Fjt3B4GtxxEwObp?ext2=copy_link>
（WorkBuddy 发布的对话分享页，页面标题「审查UI视觉与交互体验」）

**审查日期**：2026-10-06

## 0. 审查方法与事实基线

页面不是一个普通 HTML 文档，而是两层结构，这决定了后面很多问题的成因：

| 层 | 结构 | 说明 |
|---|---|---|
| 外层「壳」 | `main.publish-page` → `div.publish-page__viewport`(`overflow:hidden`) → 全屏 `iframe`，另加 3 个悬浮控件 | 只负责套壳与悬浮入口 |
| iframe 内「阅读器」 | `div.stv-container` → `header.stv-header`(56px) + `div.stv-messages` | 承载标题、免责声明、全部消息内容 |

采集方式：真实 Chromium（headless）+ CDP，`1440×900`（DPR 2）与 `390×844`（DPR 2–3）双视口，穿透跨域 iframe 与 OOPIF 逐元素读取计算样式与几何盒；对比度按渲染后的令牌值计算（非截图取样）；关键区域另做 3–4 倍局部放大复核。

事实基线（用于后文所有数字）：

- 桌面文档高 `5495px`，移动端 `7998px`；滚动**全部发生在 iframe 的 `body`**（外层 `overflow:hidden`，自身只有 900px 高、不滚动）。
- 桌面内容列：`x=303, w=834`；移动端内容列：`x=28, w=334`。
- 页面级横向溢出：**无**（移动端 `scrollWidth 390 = viewport 390`）——这一点是达标的。
- 正文字号 15/16px，元信息 12–14px。

## 一、严重（阻断或明显误导，优先修）

### S1 · 外层 `<meta viewport>`：禁止页面缩放

**区域**：外层壳 `<head>`
**表现**：`width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no, viewport-fit=cover`，桌面与移动端一致。
**影响用户的原因**：这是一个以长文阅读为主的页面，正文要连续读 5000–8000px。用户一旦觉得字小（正文 15–16px、表格 14px、免责声明与"上下文已压缩"仅 12px），**没有任何自救手段**——双指缩放被明确禁用。这是全页唯一阻止用户自行补偿小字号的机制，属 WCAG 1.4.4（调整文本大小）不达标。对轻度视力障碍者、驾驶/走动中阅读的场景影响尤其大。
**修改建议**：删掉 `maximum-scale=1.0` 与 `user-scalable=no`，保留 `width=device-width, initial-scale=1.0, viewport-fit=cover`。若担心布局在放大后错乱，应先修 S2 的表格溢出，而不是锁死缩放。

### S2 · 核心证据表必须横向滚动才能读

**区域**：消息内 `cr-table-block`（"最该先修的 8 项（P0）"表格）
**表现**：`.cr-table-block__scroller` 桌面 `scrollWidth 1422 / clientWidth 834`（**1.7 倍溢出**），移动端 `clientWidth 390`。「根因定位」列单元格实测宽 `1159px`、起点 `x=565`，即桌面也直接越过 1440 视口；截图（桌面 A-d2、移动 C-m4）中该列文字被硬切在容器右缘，**没有任何"可以左右滑"的视觉提示**（无渐隐遮罩、无滚动条暗示）。
**影响用户的原因**：这张表是全文最关键的"证据链"（每条问题对应的文件:行号）。读者读到"底部导航标签与目标不是一回事"时，必须先把表格横向拖动才能看到它的依据；在移动端这一步几乎等于劝退——手指横拖会与页面纵滚打架，且切掉的正是最有价值的一列。
**修改建议**：
1. 移动优先改版：把每一行改成一张卡片，「问题」作卡片标题，「根因定位」作正文（`文件:行号` 用行内代码样式 + 独立一行）。
2. 桌面保留表格，但两列宽度用 `min-width` 约束在容器内（如 `26% / 74%`），长路径用 `word-break` 折行而不是撑宽。
3. 若仍允许横向滚动，给 `.cr-table-block__scroller` 加右缘渐隐遮罩，并显式暴露滚动条。

### S3 · 折叠头（「已完成 13m57s」「过程消息」）键盘不可操作、无展开语义

**区域**：`header.cr-collapse__header`
**表现**：DOM 是 `<header class="cr-collapse__header"><span class="cr-collapse__title">已完成 13m57s</span><span class="cr-collapse__icon" aria-hidden="true">…</span></header>`；实测 `tabIndex=-1`、无 `role`、无 `aria-expanded`、无内部可聚焦元素，但 `cursor:pointer`、`height:26px`。
**影响用户的原因**：这类折叠块是"过程消息 / 推理过程"等大段内容的**唯一入口**。鼠标用户点得开，键盘用户 Tab 到不了（因为 `tabIndex=-1`），读屏用户听不出"这是可展开控件、当前是收起还是展开"。等于把页面里体量最大的一部分内容对键盘与读屏用户整体关闭。
**修改建议**：改用 `<button aria-expanded="true|false" aria-controls="...">`（或原生 `<details><summary>`）；标题行用 `padding: 10px 12px; margin: -10px -12px` 把命中区从 26px 撑到 ≥44px；给 `:focus-visible` 加可见描边。

### S4 · 「复制」操作只靠 `:hover` 显隐 → 触屏不可达

**区域**：消息右上角工具条 `.cr-toolbar` / `button.cr-icon-button`
**表现**：CSS 中 `.cr-toolbar { opacity: 0; pointer-events: none; }`，全站**唯一**的揭示规则是 `.cr-frame--right:hover .cr-toolbar { opacity: 1; pointer-events: auto; }`（`.cr-queue-guidance:hover` 同理）。样式表里**没有** `@media (hover: none)` 兜底，也**没有** `:focus-within`。实测默认渲染（触屏用户代理 + 触屏模拟，`H2-clean-top.png`）该按钮完全不出现，且 `elementFromPoint` 打在它的坐标上命中不到它（`pointer-events:none`）。
**影响用户的原因**：分享页最自然的动作就是"复制这段结论/这段提示词"。而这条路径在手机上根本没有入口——用户看不到、也点不到，只能退化成手动长按选中文本（而页面同时还在 S1 里禁用了缩放，长按选择的体验更差）。
**修改建议**：补两条兜底——`.cr-frame--right:focus-within .cr-toolbar { opacity:1; pointer-events:auto }`，以及 `@media (hover: none) { .cr-toolbar { opacity:1; pointer-events:auto } }`（触屏常显，或收进右下「更多操作」）。同时把 `24×24` 命中区提到 ≥44×44。

### S5 · 源码里直接写死 `outline: none`，键盘完全看不到焦点

**区域**：`button.cr-icon-button`（复制、更多操作等图标按钮）
**表现**：样式表中存在 `.cr-icon-button:focus { outline: none; }` 与 `.cr-icon-button:focus-visible { outline: none; }`。实测聚焦后 `outline-style: none`、`box-shadow: none`，即**没有任何替代焦点指示**。（页面上其余组件是有焦点样式的，例如 `.cr-menu-item:focus-visible { outline: 1px solid var(--cr-border-default) }`，说明设计系统本身知道该怎么做，这里是单点遗漏。）
**影响用户的原因**：`outline:none` 而无可视替代，键盘用户在图标按钮上"失明"——不知道自己现在在第几个按钮、按回车会发生什么。WCAG 2.4.7（焦点可见）明确不达标。叠加上 S4，这个按钮对键盘用户是"既看不见、又不知道焦点在哪"。
**修改建议**：`.cr-icon-button:focus-visible { outline: 2px solid var(--cr-brand, #1470b4); outline-offset: 2px; }`；把 `:focus { outline: none }` 这条删掉（它连鼠标点击的默认环也一起吃了，属于误伤）。

## 二、中等（明显影响体验，应排入下一批）

### M1 · 悬浮控件在滚动中段遮挡正文

**区域**：外层壳 `.chat-with-workbuddy-entry`
**表现**：主 Pill `243×48` 固定底部居中（桌面 `@599,822`，移动 `@74,766`），「×」`39×39` 挂其右上角（桌面 `@818,803`）。而 iframe 内 `.stv-messages` 只在**文档末尾**留了 `padding-bottom: 120px`。滚动中段时三者直接压在内容上：桌面 A-d2 压住正文段落，A-d4 压住表格行，4 倍放大图 E-chart-zoom 压住"卡片翻转与切词是硬切、零动效"整行（含它的条形）。
**影响用户的原因**：遮挡位置随机且不可预测，用户必须靠"稍微滚一点再读"绕过；被压住的恰好常是那几行的关键结论。底部内边距只能保护文档末尾，解决不了中段遮挡。
**修改建议**：滚动时降低存在感——滚动中 `opacity:.4 + transform:scale(.96)`，停止 1.2s 后恢复；或改为"仅当滚动接近底部时出现"；或用 `IntersectionObserver` 让 Pill 避开正文列（桌面靠右贴边而非居中压字）。

### M2 · 移动端两个悬浮控件语义重叠、互相抢焦点

**区域**：外层壳 `.copy-link-fab` + `.chat-with-workbuddy-entry`
**表现**：移动端同时存在 `.copy-link-fab`（`44×44` 白圆、`aria-label="复制链接"`、`@330,680`）与主 Pill（`243×48` 黑底、`@74,766`），两者都占据底部区域、都表达"带走这个页面"的意图。桌面端实测只有 Pill（截图与按钮枚举中均无 FAB）。
**影响用户的原因**：两个都是"复制/分享"，用户要花一次决策判断该点哪个；黑 Pill 体量远大于白圆，视觉上白圆像被压住的次要元素，但它承担的功能并不次要。移动端底部同时被两个悬浮物占据，进一步缩小了可读区。
**修改建议**：移动端合并为一个入口——主 Pill 展开后内含"复制链接"，或把"复制链接"收进页头；若都必须保留，则让 FAB 与 Pill 在垂直方向共用一条基线并向两侧分开，避免视觉堆叠。

### M3 · 隐藏态的悬停工具栏仍在 Tab 序列里

**区域**：`div.cr-widget-header-actions-group`（卡片上的「下载到本地」「更多操作」）
**表现**：规则为 `.cr-widget-header-actions-group { opacity: 0; pointer-events: none; }`，靠 `.cr-widget-card:hover / :focus-within` 才变 `opacity:1`。但内部两个 `button` 的 `tabIndex=0`。实测用 `element.focus()` 直接聚焦内部按钮时，容器 `opacity` 仍为 `0`（`{focused:true, gOp:"0"}`），且 `visibility` 是 `visible`（并非 `hidden`）。
**影响用户的原因**：`opacity:0` 不会把元素移出 Tab 序列与无障碍树，所以键盘 Tab 可能落到一个**完全看不见的按钮**上——按下去会触发下载，用户既不知道焦点在哪，也不知道触发了什么。属 WCAG 2.4.11 / 2.4.7 类风险。
**修改建议**：隐藏态用 `visibility: hidden`（配 `transition: opacity .2s, visibility 0s .2s`）或 `display:none`；若必须用 `opacity`，则隐藏态同步设 `tabindex="-1"` 与 `aria-hidden="true"`，显示时再恢复。

### M4 · 移动端多处命中区小于 44px

**区域**：`cr-icon-button`、`cr-collapse__header`、`cr-widget-primary-action`、外层 `chat-with-workbuddy-entry__close`
**表现**（移动端实测盒模型）：复制按钮 `24×24`；更多操作 `24×24`；「下载到本地」`101×24`（高 24）；折叠头「已完成 13m57s」`117×26`；「×」关闭 `39×39`。图标本体更小（`--cr-icon-button-icon-size: 14px`）。
**影响用户的原因**：26px 以下的命中区在拇指操作下误触率高，连续多个 24px 按钮纵向排列时几乎必然会点错（复制 vs 更多操作相邻）。「×」39px 也偏小，且它是"关掉这个悬浮条"的唯一出口。
**修改建议**：统一用 `padding` 或伪元素把命中区撑到 `44×44` 以上（视觉尺寸不变，仅扩热区），例如 `.cr-icon-button::after{content:'';position:absolute;inset:-10px}`（容器 `position:relative`）；相邻图标按钮间距 ≥8px。折叠头与「下载到本地」同理。

### M5 · 次级文字对比度 3.94:1，不达 AA

**区域**：消息时间戳「10月1日 23:48」(14px)、状态行「**已完成 13m57s**」(15px)、分隔标签「上下文已压缩」(12px)
**表现**：三处同用 `color: rgba(0,0,0,0.5)`（令牌 `--cr-text-tertiary: #00000080`）落在 `#fafafa` 上，实测对比度 `3.94:1`。WCAG AA 对正文（<18.66px 非粗体）要求 `4.5:1`。
**影响用户的原因**：「已完成 / 已取消」是判断"这段内容是结论还是过程、有没有被中断"的唯一线索，而它恰好是最淡的一行；「上下文已压缩」标记着"上文被折叠了、信息有丢失"，同样是关键状态提示。淡到读不清，用户会误以为页面"没加载完"。
**修改建议**：把 tertiary 令牌从 `#00000080`（50% 黑）提到 `#00000099`（60% 黑，≈`4.9:1`）或 `#000000a6`（65%，≈`5.6:1`）；「已完成/已取消」这类状态标签建议单独用 14px + 62% 并加字重 500，靠权重而非淡度做层级。

### M6 · 行内文件链接 4.49:1，卡在阈值下

**区域**：`.cr-inline-code.cr-path`（如正文中的 `ui-ux-review-20261001.md`）
**表现**：文字 `rgb(20,112,180)` on 背景 `rgb(233,238,242)`，实测 `4.49:1`——比 AA 要求 4.5:1 差 0.01，属"贴着线但没及格"。
**影响用户的原因**：这既是最需要看清的文本（文件名、路径），又是 14px 小字，还在彩色底上。低视力用户读路径最容易串行错字；它同时是点击目标，看不清会导致点错。
**修改建议**：文字加深到 `#0f5f9e`（≈`5.2:1`），或背景降一档到 `#f1f5f8`；两者选其一即可留出余量，建议目标 ≥`4.8:1`。同时给它加 `text-decoration: underline`（默认态）以满足"链接不能只靠颜色区分"（WCAG 1.4.1）。

### M7 · 加载期没有骨架屏，图表区先出现空白卡片

**区域**：外层壳 `.publish-bootstrap-loading` + iframe 内 `cr-widget-card`
**表现**：外壳自带的 spinner 在 React 挂载时就被移除（实测导航后 3s 已 `spinner:false`），而 iframe 内 1.8MB 会话数据要 5–15s 才渲染完（本轮实测首次加载 10–15s，二次 5s 左右）。这段窗口期是**纯白页面 + 底部一个悬浮 Pill**，无任何进度反馈。另外图表 widget 在自己的 iframe 里异步绘制，绘制前先渲染出一张 `336×86` 的**空白圆角卡片**（内含 60px 高的空 iframe，见 `H2-clean-top.png`）。
**影响用户的原因**：白屏会被判断为"链接挂了"——尤其这是别人发来的分享链接，首次访问者没有耐心等 10s。空卡片更糟：它看起来像"图表加载失败"，用户可能直接跳过这段内容，而这是全文的问题分布概览。
**修改建议**：① 把 bootstrap spinner 的生命周期延长到 iframe `load` 事件之后再移除；② 消息区渲染 3–4 个灰阶骨架块（标题条 + 段落条 + 卡片块）；③ 图表卡先画占位条形（固定高度灰条）而不是空卡片，避免"空 → 满"的跳变。

## 三、轻微（一致性债，可批量处理）

### P1 · 无深色主题，且外壳存在"假深色"闪烁

**表现**：外壳 `<style>` 里写了 `@media (prefers-color-scheme: dark){ html, body { background:#181818; color:#e6e6e6 } }`，实测暗色偏好下外壳 `body` 变为 `rgb(24,24,24)`；但 iframe 内恒为 `rgb(250,250,250)` 亮色（分享数据 `theme:"light"`）。结果是暗色截图与亮色截图**字节完全相同**——用户先看到一瞬深色，随后整页仍是刺眼白底。
**建议**：二选一。要么给分享内容加 dark 令牌集（`stv-*` / `cr-*` 各一套），要么删掉外壳那段 `prefers-color-scheme` 规则，避免"闪一下深色再变白"的廉价感。长文阅读页尤其值得做真深色。

### P2 · 字号与图标标尺不收敛

**表现**：实测出现 `12 / 13 / 13.3333 / 14 / 15 / 16px` 六档，其中 `13.3333px`（浏览器 `font-size: small` 级别的异常值）与 `13px` 并存，差 0.3333px——肉眼看不出，但说明有元素没走令牌。图标尺寸混用 `12 / 14 / 16 / 24px` 四档（同一条消息里折叠箭头 12px、图标按钮内 14px、widget 图标 16px）；SVG 描边 `0.975px` 与 `1px` 混用。
**建议**：字号收敛为 `12 / 14 / 16 / 20` 四档并全部走令牌；图标统一 `16px`（密集处 14px），描边统一 `1.5px`；把 `13.3333px` 的来源（多半是某个 `font-size: small` 或 em 继承）定位并改掉。

### P3 · 标题语义层级缺失

**表现**：页面标题是 `span.stv-header__title`（16px/600），不是 `h1`；iframe 内 10 个章节标题「最该先修的 8 项（P0）」「视觉层面最系统的一个发现」等**全部是 `h2`**，文档中没有 `h1`。
**建议**：标题改 `<h1>`，章节保持 `h2`、子项用 `h3`。对读屏用户来说，"按标题跳转"是长文最重要的导航方式。

### P4 · 「×」关闭按钮对比度与尺寸双不达标

**表现**：`39×39`、`background: rgb(163,163,163)`、白色 `×` 字形，实测对比度 `2.52:1`——低于图形元素要求的 `3:1`，也低于文字要求。
**建议**：背景改 `#6b6b6b`（白字 ≈`5.7:1`），或改为浅底 + 深色描边图标；尺寸撑到 `44×44`。

### P5 · 图表只有长度、没有数值

**表现**：条形图仅靠长度表达量级，无条数值标签、无坐标轴刻度，只有 5 条极淡竖网格线（见 2 倍放大 `E-chart-zoom.png`）。三色图例（红 P0 / 琥珀 P1 / 灰 P2）仅靠色相区分，红与琥珀在红绿色盲下难以分辨，也没有形状或纹理差异。
**建议**：条尾补数值（如「7 项」）；图例色块加一档明度差或改用"实心/斜纹/描边"三种填充；保留图例色块的小方块并放大到 ≥12px。

### P6 · 页头标题与正文左边缘错开 16px

**表现**：桌面 `.stv-header__title` `x=287`（所在容器宽 866），正文列 `.cr-document` `x=303`（宽 834）；移动端标题 `x=12`（header padding 12px），正文 `x=28`。**两端一致的 16px 错位**，说明标题容器与内容列是两套宽度（866 vs 834），没有共用同一条栅格。
**建议**：让 header 内部容器与 `.cr-document` 用同一个 `max-width` 与同一组左右内边距（建议统一到 834px / 桌面 24px、移动 16px），标题与正文左对齐。

## 四、整体体验评价

**总体印象：内容质量高，容器质量为中下。** 这个分享页承载的内容（一份结构清晰、带证据链和分级的问题清单）本身是有价值的，阅读器的基本骨架也立得住——正文字号 15–16px、行高舒展、内容列居中、移动端无横向溢出、列表与表格样式统一，属于"安静、不抢戏"的阅读型排版，方向是对的。

问题集中在三处系统性的地方：

1. **可达性几乎完全依赖鼠标。** 复制、展开、下载、更多操作这四类交互，分别踩中"仅 hover 显隐""tabIndex=-1""opacity:0 仍可 Tab""`outline:none`"四个不同的坑。四条叠加的结果是：键盘用户和触屏用户在页面上能做的事，比鼠标用户少掉一大半。这不是零散 bug，而是缺少"每个交互都要有 hover / focus / touch 三态"这条约束。
2. **长文阅读的"读"这件事没被当成核心场景。** 禁用缩放（S1）、核心表格要横拖（S2）、关键状态字 3.94:1（M5）、图表无读数（P5）——四件事都在削弱"把内容读懂"这个唯一目标。
3. **加载与状态反馈缺位。** spinner 撤得太早、图表先画空卡片、隐藏态元素还在 Tab 序列里，都是"状态"没有被完整建模的表现。

做得好的地方也值得保留：内容列居中且宽度克制、移动端零横向溢出、折叠块默认收起降低了信息密度、图例用色与语义（红=阻断/琥珀=影响/灰=一致性债）对应清晰。

### 优先级最高的 3 项改进

| # | 改进项 | 为什么排第一 |
|---|---|---|
| **1** | **放开缩放（S1）＋ 修焦点可见性（S5）** | 两项改动量最小（各 1–2 行 CSS/meta），但直接决定"视力不佳的用户能不能读完""键盘用户能不能用"。是所有可达性问题的分母，且零风险。 |
| **2** | **把「复制」与折叠头改成三态可达（S4 + S3）** | 这两处覆盖了页面最高频的两个动作（复制内容、展开过程）。补 `:focus-within` + `@media (hover:none)` 兜底、把 `<header>` 换成 `<button aria-expanded>`，一次就能同时救回触屏与键盘两个用户群。 |
| **3** | **P0 表格移动优先改版（S2）** | 这是唯一"内容本身因布局而失效"的问题——最有价值的证据列在移动端基本读不到。改版收益直接落在核心信息上，且顺带解掉桌面 1.7 倍溢出。 |

顺带建议：M5（3.94:1）、M6（4.49:1）、P4（2.52:1）、M4（24px 命中区）都是**改令牌就能批量修**的类型，建议与第 1 项一起做成一次"令牌 + 热区"批处理，一次过覆盖 4 个条目。
